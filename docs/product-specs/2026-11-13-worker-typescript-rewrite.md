# worker TypeScript 重写规格

状态：待实施。现有生产版本仍以 Python worker 运行，并支持原有模型选项；本规格定义重写后的目标行为。

## 目标和范围

将 Locus 自有 `worker/` 的 Python 运行期替换为 TypeScript。迁移覆盖媒体处理、ASR、模型管理、网页笔记保存、任务存储、工作间工具、LLM 连接测试和数据存储校验。除本规格明确调整的模型选项外，产品现有功能、用户数据和安全边界持续有效。

- 视频、音频和网页来源继续使用现有流程；已保存的媒体任务和网页笔记可读取、编辑和继续处理，历史、合集及用户设置保持可用。
- 工作间的要点总结、文字稿解剖、启发灵感、生成文字稿、文字稿整理及自动标题继续支持现有入口、产物、确认、计费、取消与失败行为。托管模型和 BYOK 按现有规则运行；草稿检索保留现有服务端 anysearch 行为。
- ASR 仅提供当前默认的 `iic/SenseVoiceSmall-onnx`，设置、模型准备和新任务统一使用此模型；不再提供 PyTorch 模型 `iic/SenseVoiceSmall` 的选择和运行时组件下载。ASR 内部保留清晰的模型适配接口，后续可在不重写任务流程的前提下接入其他模型。
- TypeScript worker 使用通用 ONNX 运行时直接加载生产模型文件，沿用 `<根>/models/onnx/` 缓存与 `iic/SenseVoiceSmall-onnx` 标识；前端、CTC 解码、文本清理与 FSMN VAD 由 TypeScript 实现，识别行为与现有生产路径一致。
- worker 运行期沿用安装包已有的 Deno，原生依赖随包外置，不额外引入第二套 JS 运行期；原生库必须与随包依赖同目录，不得回退使用操作系统自带的旧版运行时。
- 受支持平台为 Windows x64 与 macOS Apple Silicon。macOS Intel 不再提供安装包、运行时组件与更新，已有 Intel 用户停留在最后一个支持该平台的版本。
- 升级时，原设置选为 `iic/SenseVoiceSmall` 的用户一次性迁移到 `iic/SenseVoiceSmall-onnx`，并在设置中明确提示模型已变更；原本选用 ONNX 的用户继续使用当前设置，已下载的 ONNX 模型文件直接可读取，无需重新下载。其他设置不变，未知模型设置须明确报错，不得当作旧 PyTorch 设置静默迁移。
- 已有 PyTorch 模型文件、运行组件保留在用户数据目录，不自动删除；历史文字稿、任务及其原始模型标识继续可读。旧模型文件是否可参与后续数据位置迁移和恢复，按数据完整性验证，不能要求新 worker 执行旧 PyTorch 组件。
- 核心 ASR 模型继续在用户提交已验证任务且所选模型缺失时按需下载；启动时不自动下载。下载进度、取消、完整性校验、离线及失败行为保持可见。安装包不内置 ASR 权重、LLM key、云端模型或用户私有配置。
- 现有 ONNX 缓存直接复用，沿用现有目录结构、`MODEL_VERSION.txt` 就绪标记、SHA-256 校验、按需下载与原子提交；缓存缺失时按现有可观察路径准备，缓存损坏不得视为可用。

## 进程、数据与安全

- 继续由 Rust 监督 worker，保留固定绝对超时、已验证进度的空闲超时、取消及进程树终止。受限 stdin、结构化结果、进度事件和错误处理继续遵守现有边界；模型可选值收窄涉及 `contracts/desktop-worker-contract.json`、前端、Rust 与 worker 的一致更新和版本兼容验证。
- 任务清单、文字稿及 AI 产物沿用既有 schema、来源核验、原子写入、多文件事务恢复和数据位置许可；旧任务兼容必须使用真实旧任务验证。
- 视频、音频、文字稿、模型缓存与本地历史默认留在本机；账号服务不接收这些内容或 cookie。公开或已授权的来源、模型下载、用户确认的 LLM 调用和现有草稿检索继续遵守各自的网络与隐私边界。
- 发行包内不再包含供自有 worker 使用的 Python 运行时。用户允许官方独立 yt-dlp 程序内置 Python，作为唯一第三方例外；继续支持现有公开或已授权来源及下载行为。ffmpeg 和 ffprobe 继续提供现有媒体处理行为，音频归一化参数保持 `-vn -ac 1 -ar 16000 -c:a pcm_s16le`。第三方组件分发前核实许可、来源、完整性与受支持平台上的运行。

## URL 下载器

- `--request-stdin` 是 URL 任务的唯一入口。请求为 `contract_version` / `url` / `asr_model` 三键闭集，非法请求返回固定文案的 `INVALID_REQUEST_PAYLOAD` 且阶段停在等待输入，不发起任何下载。URL 只去掉首尾空白，其余字符原样保留。
- 下载调用官方独立 yt-dlp 可执行文件：Windows 用 x64 发行文件，macOS 用 universal 发行文件。发行包按固定版本与官方 SHA-256 校验分发这两个文件，运行时禁止自动更新，也禁止回退到系统 Python 的 `yt_dlp` 模块。
- 官方 PyInstaller 打包的可执行文件包含 GPLv3+ 许可代码，组合作品按 GPLv3+ 分发；发行包须随附许可文本与对应源码的获取方式。官方 zipimport 版与源码包只含 Unlicense / ISC / MIT 许可代码，不能满足 Windows 与 macOS 的独立运行要求，因此不作为发行资产。
- 来源识别、三平台传输与字幕、失败、超时、取消、媒体归一化、ASR 与任务清单沿用现有流程；只处理公开或已授权来源，网络与隐私边界不变。下载命令参数、YouTube 失败分类、字幕解析、产物定位与下载编排按现有实现逐项复现；HTML5 实体表使用成熟的第三方库，发行包须随附该库许可文本。
- URL 任务的 `task.json` 与现有 Python 清单逐字节一致：任务 id 为 `时间戳-平台-稳定 ID[-p分P]`，来源字段只写 `source_url` / `source_identity` / `platform`，不写 `source_kind`；规范 URL 不含分享 token，来源身份在写入与读回时都要重新验算。清单是宿主、Python 与 TypeScript 共读的状态，任何新增或改名的键都视为破坏性变更。
- `--request-stdin` 已接通完整链路：请求解析 → 来源解析（直连 + 三平台短链）→ 建任务 → 官方独立 yt-dlp 下载 → 视频/音频校验与归一化 → 平台字幕或本地 ASR → 写文字稿与清单。宿主通过 `APP_YTDLP_PATH` 注入随包可执行文件；未注入时按平台在 `<项目根>/bin/` 下找 `yt-dlp.exe`（Windows）或 `yt-dlp_macos`（macOS），找不到即返回固定 `VIDEO_DOWNLOAD_FAILED`，不回退系统 Python。
- 三平台 fallback 传输层全部接通：抖音走分享页 SSR 解析、bit_rate/探测候选、按大小去重排序、单候选续传重试、8 MB 档位进度与 3 次分享页重试；小红书走公开笔记页 `__INITIAL_STATE__` 解析、候选流九元组打分、主备地址有序下载与字幕轨下载；B 站走公开 API（`view` / `playurl`）、DASH 音视频轨选择、分片下载与 ffmpeg `-c copy` 合并，番剧、影视、课程与 DRM 内容明确拒绝。三者均由跨语言基准逐项验证。
- 小红书字幕探测在 yt-dlp 成功路径上自动执行：只接受小红书 CDN/主站的 https 字幕地址，2 MiB 上限，任何解析或网络失败都收敛成「没有字幕」，不影响视频任务。
- 可靠下载（`src/download-reliability.ts`）是各平台共用的最后一道把关：状态码、Content-Range、Content-Type、声明大小与实际写入逐项校验，写盘先落 `.part` 再原子改名，断流/提前结束保留部分文件供续传。错误码与判定顺序与 Python 一致。
- `--download-runtime-component` 服务旧 PyTorch 运行时组件下载，新版本不提供该模式；用户数据目录里已下载的旧组件继续保留，不自动删除。

## ASR 与验收

现有默认路径使用 `funasr_onnx` 和 FSMN VAD。重写后使用同一模型权重、同一 FSMN VAD 文件与相同的前端、分段和解码规则，以现有 ONNX 生产路径为唯一 ASR 质量与性能基线；前端张量、CTC 解码结果与分段时间戳须与基线逐项比对。接口职责和适配边界见 `docs/design-docs/2026-11-13-typescript-worker-asr-boundary.md`。

新实现必须验证长语音分块、句首丢词、跨停顿分段、时间戳、重复文本、无语音和纯音乐等情况。识别质量与性能使用同一固定语料、同一硬件和可复现的 Python ONNX 基线比较；验收全程自动化，自动参考文本须独立于候选生成，其结果是质量代理指标。无语音时沿用 `ASR_EMPTY_TRANSCRIPT` 失败语义，不写入虚构文字。具体门槛和执行方式以执行计划为准。

发布前验证各受支持平台的打包应用、原生依赖、下载、旧数据、任务取消、异常恢复和工作间。安装包体积按 Windows x64 与 macOS Apple Silicon 的实际构建与现有版本对比记录，不能预先假定完全相等。
